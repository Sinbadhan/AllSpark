# PDR-001：v1 从功能集合收敛为 24 小时生存行动闭环

- **状态：** Accepted
- **日期：** 2026-07-15
- **补充决策：** 2026-07-16，全生命周期持续可达的立即危险入口
- **决策人：** 产品所有者
- **关联：** `PRD.md`、Linear `SHA-158`

## 背景

AllSpark 的工程质量已经达到较强的 Release Candidate 水平：架构、CI、安全边界、覆盖率、CSP、可访问性自动化和限定桌面 PROCESS 模式均有可重复证据。但端到端产品审计发现，首次启动仍允许用户在没有资源单位、没有关键环境数据、没有目标和没有行动计划的情况下进入系统。

因此，当前主要风险不是功能缺失，而是功能没有组成一个能够交付结果的主路径。对生存决策产品而言，空仪表盘、伪精确状态或不可审计建议的风险高于少一个外围模块。

## 第一性原则拆解

### 核心变量

1. 用户可能处于高压力、低认知带宽和完全离线环境。
2. 系统输入天然不完整，未知不能被当作零或安全值。
3. 生存建议属于高风险输出，正确性、来源和适用条件必须可解释。
4. 用户需要的是下一步行动，不是模块目录或通用知识长文。
5. 离线产品必须独立完成安装、初始化、决策和执行记录。

### 不可妥协约束

- 无单位数据不得触发生存判断。
- 未知数据不得产生默认安全结论。
- 高风险建议必须显示依据和边界。
- 初始化成功必须带来首份可执行计划。
- 正在发生的生命危险不能等待 5 分钟评估或硬件/模型配置；首屏必须提供确定性的快速分流入口。
- 危险可能发生在初始化后的任意时刻；立即危险入口不能与一次性 onboarding 生命周期绑定。
- Testing/Experimental 能力不得被表达为已验证可用。

## 证据

- 默认资料可以完成 Web 初始化，初始化后五项资源均未配置。
- 当前 Web 首次启动顺序是语言、硬件、AI 模型、生存者档案；健康和紧迫程度位于最后一步，正在发生危险的用户没有首屏快速入口。
- 仪表盘直接显示 Phase 1，但没有足够数据证明阶段判断。
- 执行中心没有自动目标或任务，空状态缺少下一步行动。
- 资源录入使用通用数值字段，界面没有明确单位和多人上下文。
- 用户陈述“两天饮用水”后，系统返回净水知识，但没有确认人数、更新资源、生成任务或重排计划。
- 当前知识库 152 条双语记录对应 76 个主题；大量 `field_tested` 标记缺少随包可审计的现场证据。
- System/Config 暴露较多内部状态，supported、enabled、installed、configured、running、verified 的语义仍容易混淆。
- 仓库和 Linear 中没有发现正式用户研究、可用性试点或产品成功指标；现有成功标准以工程指标为主。

### 决策后的追加代码复审

方向确认后继续检查当前 main `fc62f78`，发现以下实现风险，并登记为 Linear SHA-247 至 SHA-251：

| 发现 | 运行时/代码证据 | 产品风险 |
|------|-----------------|----------|
| 火源续航忽略每日消耗 | 10 次、2 次/日返回 240h，正确为 120h | 延迟补充行动和预警 |
| 未知关键资源被当作无限 | 水未配置、食物充足时返回 Phase 2 | 把信息缺口表达为安全余量 |
| 资源写入缺少边界 | 消费 -5 会增加库存；NaN 触发未处理数据库异常 | 污染评估或导致不可恢复错误 |
| 验证等级形成循环信任 | unknown 来源自称 field_tested，凭同分类关键词记录继续得到 field_tested | 外部知识可自我提升可信度 |
| Web 初始化不是原子事务 | 先写 initialized，再加载引擎 | 失败后遗留半初始化状态 |

这些问题强化了本决策的必要性：数据真值、知识信任和初始化完成语义必须在服务层闭环，不能只调整界面文案。

### 2026-07-16 全生命周期复审补充

讨论侧以新数据库完整走通首次评估 → 初始化 → 状况 → 行动 → 知识后，确认初始化页入口在初始化完成后消失。由于 Linear workspace 达到 free issue limit，发现以唯一 tracking key `P1-NEW-20260716-A` 记录在 SHA-158 评论 `0b932663-2a8b-4975-9c5d-e0db79ab6696` 与 SHA-236 评论 `8ef19eb3-e815-40cd-bab9-73593a6f801c`，不得因缺少独立 SHA 编号而遗漏。

本轮决定：

1. 状况、行动、知识等常态核心页面必须一次操作进入立即危险流程；移动端不得要求先打开导航菜单。
2. 初始化页与常态产品壳复用同一 dialog、前端控制器、API、确定性规则和审阅目录，不复制医学或危机规则。
3. 流程事实只存在于当前页面内存；关闭或刷新清除，不写入初始化、健康、资源、任务或浏览器存储，焦点返回触发控件。
4. 常态入口使用稳定的警示色边框而非持续高强度红色警报；dialog 内维持危险层级视觉。这样同时满足快速发现与降低警报疲劳。
5. 自动化真实 Chrome 已覆盖中英文、状况/行动/知识、键盘、焦点 trap/restore、桌面、移动、窄桌面、200% reflow 等价矩阵、CSP 与无状态写入；精确运行证据维护在上述 Linear tracking 评论。

该补充只改变入口的生命周期可达性，不扩建临床诊断、自动联系紧急服务、后台监听或自伤风险评估。SHA-241 的具名领域复核继续阻断 Stable；浏览器交互通过不能替代内容专业复核。

## 方案比较

### 方案 A：保持 16 模块并直接发布 Stable

- **优点：** 发布最快；保留现有叙事宽度；无新增产品范围。
- **缺点：** 首次使用不产生明确价值；外围功能分散资源。
- **风险：** 用户把 RC 能力误认为真实应急保障；错误输入和不可审计内容会放大安全责任。
- **结论：** 拒绝。

### 方案 B：保留工程能力，收敛 Stable 主路径

- **优点：** 复用现有架构；把工作集中到最高价值闭环；外围能力无需删除。
- **缺点：** 延后 Stable；需要调整初始化、数据契约、任务系统和信息架构。
- **风险：** 如果只改 UI 而不统一数据模型和评测，仍会形成表面闭环。
- **结论：** 采用。

### 方案 C：降级为离线知识阅读器

- **优点：** 产品承诺更容易兑现；安全边界更简单。
- **缺点：** 放弃 AllSpark 已有规则引擎、资源评估和任务系统的核心差异化。
- **风险：** 产品价值退化为已有离线百科的替代品。
- **结论：** 暂不采用；如果 M1-M3 无法达到安全门槛，应重新评估。

## 决策

v1.0.3 Stable 以“Assess → Decide → Act → Reassess”的 24 小时行动闭环为唯一一级产品目标。当前工程 RC 保留，但 Stable 发布由以下四组门禁阻断：

1. 最小状况评估和统一资源单位。
   其中包括不依赖模型、硬件配置或完整初始化的“立即危险”首屏入口。
2. 可解释的 24 小时行动计划和场景安全评测。
3. 建议到任务再到重新评估的执行闭环。
4. 可审计知识、真实能力状态、明确 RC 边界和非开发者离线交付。

## 假设与不确定性

- 假设主要用户仍是极客和生存主义者；这支持高信息密度视觉，但不支持模糊状态或开发者式安装成为永久前提。
- `field_tested` 可能存在仓库外证据，但当前离线包和 UI 无法审计；在证据进入产品前按缺失处理。
- 本轮未验证真实硬件、Windows NVDA、Docker daemon 和真实 GGUF 下载/推理；这些继续保持 Testing/Experimental。
- 尚无足够目标用户研究证明“5 分钟”是最佳阈值；五画像 AI 预演估计普通高压用户需要约 7-10 分钟获得首份行动，且不能替代真实用户。5 分钟继续作为待 SHA-246 至少 5 名真实目标用户验证和复核的产品假设。

## 反方意见

“目标用户是极客，能够理解技术状态和手动配置”是合理反方。但极客身份不能消除压力环境、单位错误、知识来源和状态真值问题。高级入口可以保留技术细节，一级路径仍应优先保证行动效率和安全。

“当前限定 PROCESS 模式已经通过全部工程门禁”也是事实。这证明工程 RC 可用，不足以证明生存产品 Stable。两种结论必须并存，不能互相替代。

“只在状况首页提供入口，或把入口收进全局菜单，可以减少界面压力”是合理反方。但危险可能在用户查看行动或知识时发生；首页专属入口增加返回成本，移动菜单则至少需要两次操作。采用 desktop/mobile topbar 的一次操作入口，并通过较低强度的常态警示视觉、共享 dialog 和窄屏/缩放门禁控制界面压力。

## 验收方式

- 以 PRD §12.4 产品质量与场景门禁为最终验收。
- 立即危险入口需在初始化前后以同一规则/审阅目录完成独立危机场景、键盘、焦点恢复、缩放和 VoiceOver 验收；不得用普通初始化流程或单一页面通过代替。
- Linear 建立独立产品化项目，M1-M4 作为里程碑，具体 Issue 记录代码、测试、浏览器和场景证据。
- `SHA-158` 继续作为全局审计总控，Stable 结论随项目进度持续刷新。
- 每个里程碑完成后进行一次端到端复审，不用子测试或单页面截图代替完整闭环。
